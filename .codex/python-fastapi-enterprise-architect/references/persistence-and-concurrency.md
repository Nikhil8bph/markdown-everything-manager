# Persistence and concurrency

## Choose a coherent I/O model

Follow the selected database driver and client APIs. Use `async def` for awaitable I/O; synchronous route/dependency functions are appropriate for blocking stacks. Ordinary synchronous helper calls inside `async def` still block the event loop—FastAPI does not automatically offload them. Explicitly offload bounded blocking work when needed. CPU-heavy work requires the approved process/worker boundary rather than assuming async makes it parallel. Preserve cancellation and clean up resources in `finally` or context managers. See [FastAPI concurrency](https://fastapi.tiangolo.com/async/).

Set explicit bounds for fan-out, batches, query sizes, and outbound requests. Do not create unbounded `gather` calls, global mutable per-request state, or unmanaged fire-and-forget tasks.

## SQLAlchemy and transactions, when selected

Use the installed SQLAlchemy version and the selected sync/async driver consistently. A session belongs to one request/use-case unit of work; it is not a global singleton. An `AsyncSession` must not be shared by concurrently executing tasks. Give each independent concurrent unit its own session. Configure pool limits considering every application process. See [SQLAlchemy asyncio guidance](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html).

Own commit/rollback at the application transaction boundary. Repositories may query/flush within that transaction; hidden commits in helpers prevent atomic use cases. Commit must succeed before a successful non-streamed mutation response is sent. Translate expected constraint conflicts after rollback without losing the original diagnostic context.

Avoid implicit lazy-loading during async response serialization. Load the fields/relationships required by the DTO explicitly and test query counts where N+1 regressions are plausible. Apply trusted tenant/ownership and soft-delete predicates to reads and writes, including bulk operations; a DTO filter cannot repair an unauthorized database operation.

Use database constraints for invariants that must survive races. Match approved optimistic locking, compare-and-set, or locking semantics. Avoid read-then-write uniqueness checks as the sole guard. Keep slow remote network calls outside held database locks where the workflow allows it; do not invent a distributed transaction.

## Migrations

Use Alembic only when selected for SQLAlchemy; otherwise reuse the approved tool. Review autogeneration: renames, data changes, constraints, and destructive changes need explicit reasoning. Never use `metadata.create_all()` as a production migration strategy or run competing migrations from every worker's startup.

Validate a clean install and an upgrade from a representative prior schema in an isolated disposable database. Check data/backfill compatibility and the plan's rollback or forward-recovery procedure. Do not claim a downgrade is safe merely because an autogenerated downgrade exists. Never run a destructive migration on shared/live data as part of a local verification step.

## Jobs, events, caches, and idempotency

Use FastAPI `BackgroundTasks` only for best-effort in-process work where loss on process exit is acceptable. Durable jobs require the already-approved worker/broker, retries, observability, and recovery. Background work must acquire its own resources and cannot reuse a completed request's session.

When publishing approved events from a transaction, use the selected outbox/delivery mechanism. Match topic, key, payload, schema version, retry, and DLQ contracts. Consumers must apply side effects and durable deduplication atomically where required; mark messages processed only after successful durable work. Handle crash/replay cases in tests.

For mutation idempotency, match key scope, request fingerprint, concurrent duplicate behavior, expiry, and response replay to the contract. Do not equate an in-memory dictionary or an expiring cache with durable exactly-once processing. Cache keys must include the correct tenant/authorization context. Define TTL/invalidation for caches and documented retention for persistent Redis data. Infrastructure provisioning remains a separate task.
